## Benchmark results (this session)

RIFE v4.4, fp16, TensorRT backend, 1920x1088 (padded from 1080 to a multiple of 32), synthetic 1080p source clip (isolates pure GPU inference cost, no decode/encode overhead):

| Config | fps (multi=2) | Realtime factor @ 50p target | GPU util |
|---|---|---|---|
| Sequential `get_frame()`, no pipelining | 25.3 | 0.63x | ~20-30% |
| `core.num_threads=16` + `get_frame_async` sliding window, `prefetch=20`, `num_streams=4` (≈ AviSynth `Prefetch(16,20)`) | 51.7 | **1.29x** | **98-99%** |
| Wider sweep (threads 8/16/24, prefetch 20/40, num_streams 2/4/8) | 48-52 | 1.21-1.30x | — (plateau — this is the real ceiling on this GPU/model, not a request-starvation artifact) |

**Key lesson:** the naive "call `get_frame()` in a loop" pattern starves the GPU (~20% util) because VapourSynth only dispatches concurrent filter evaluation when multiple frame requests are in flight — there is no implicit prefetching. You must explicitly keep a window of `get_frame_async()` futures in flight (equivalent to AviSynth's `Prefetch(threads, buffer)`) to get real throughput. **This matters for the AviSynth port too**: whatever threading/MT-mode the new plugin exposes must support the same kind of concurrent-request pipelining (AviSynth's own `Prefetch()` should provide this from the caller's side, but the plugin's internal filter mode — `MT_NICE_FILTER` / `MT_MULTI_INSTANCE` / `MT_SERIALIZED` — and its internal inference-instance pool need to actually allow concurrent `GetFrame` calls to reach the GPU, mirroring vs-mlrt's `num_streams` + semaphore pool design.)

**Comparison:** prefetched-to-prefetched, 1.29x (TensorRT) vs 0.25-0.5x (existing Vulkan baseline) → **2.6x-5.2x faster, ~3.5x in the middle of the range.**

**Caveat:** this is pure RIFE inference throughput on a synthetic clip; no decode/encode overhead is included, whereas the AviSynth baseline number is a full-pipeline number. A true end-to-end comparison (real decode of `kuerbiskern_orig.MP4`) hasn't been done yet — see Next steps.

## Technical constraints to carry into either approach

- RIFE requires **32-bit float RGB** input (`vs.RGBS` in VapourSynth). AviSynth+ side will need YUV→RGB conversion and back (already handled by the existing Vulkan plugin, per its README — "converts input to planar format and outputs in RGBPS ... with color matrix conversion support for YUV inputs" — reuse that logic/convention).
- Frame dimensions must be padded to a multiple of 32 for RIFE v4.4 (1080 → 1088; general rule for v4.x < 4.25 is `tilesize_requirement=32`, changes for newer model variants — see `vsmlrt.py` `RIFEMerge()` for the exact table by model version).
- TensorRT engines are **not portable across GPU/driver/CUDA versions** — must be built (and cached) on first run via `trtexec`, exactly like `vsmlrt.py` already does (`get_engine_path()` / `trtexec()` in `vsmlrt.py`, ~line 1890-2233). Any AviSynth-side implementation needs equivalent build+cache logic (or just shell out to `trtexec.exe` the same way).
- NVIDIA-only. Distributing this means either bundling the ~3.7GB `vsmlrt-cuda` runtime (cuDNN/cuBLAS/TensorRT/onnxruntime DLLs) alongside the plugin, or investigating the smaller **TensorRT-RTX** variant (`VSTRT-RTX-Windows-x64.7z` in the vs-mlrt release, targets consumer RTX GPUs specifically, much smaller footprint) — not yet tested this session, worth a look since it might simplify distribution.
- Licensing: check vs-mlrt's and TensorRT's redistribution terms before shipping a bundled build to anyone outside this machine.

### Known real bugs found and fixed during this build (all in `mlrt_trt.cpp`, all fixed in the current source)

1. **Per-node plane selection used only the first clip's format.** Copied from `mlrt_ort.cpp`'s exact pattern (`avs_is_rgb(in_vis[0]) ? planes_r : &plane_y`, reused for every node) — breaks for RIFE's actual call shape, which mixes RGB clips with a grayscale (`Y32`) timepoint/mask clip in the same multi-clip array. Fixed to select R/G/B vs. Y **per node** based on that node's own format (and separately for the output frame based on the output clip's format). This same bug appears to exist in upstream `mlrt_ort.cpp` too — untested there, since RIFE via ORT wasn't re-verified this session.
2. **Error-message use-after-free.** `set_error()` returns `avs_new_value_error(d->err.c_str())` — a raw pointer into `d->err`. Initially `d` was a `std::unique_ptr`, freed (with its `std::string` member) the instant `Create_mlrt_trt` returns, before AviSynth reads the error string — surfaced as "Exception while processing ScriptEnvironment::ThrowError()" rather than the real error. Fixed by switching `d` to a raw `new TRTData()`, deliberately leaked on error paths (freed by `free_mlrt_trt()` on success) — this exact convention is what `mlrt_ort.cpp`'s `ORTData* d{ new ORTData() }` already does, for the same reason.
3. **AviSynth script `Function` calling convention:** required (unquoted) parameters in a script-defined `Function` **must be passed positionally**, not by name — `mlrt_RIFE_trt(c, engine_path="...", implementation=1)` fails with "Invalid arguments"; `mlrt_RIFE_trt(c, "...", 1)` works. Not a plugin bug, just an AviSynth+ scripting quirk worth remembering.
4. **"Delay-load Module Not Found" depends on which host app loads the plugin.** `nvinfer_10.dll` is a delay-loaded import of `mlrt_trt.dll`. Windows resolves a delay-loaded DLL's dependencies relative to the **host application's** directory (ffmpeg.exe, AvsPmod.exe, ...), not the plugin's own directory — so it worked when the runtime DLLs happened to be copied next to whichever ffmpeg build was used, and failed with a totally different ffmpeg build (or AvsPmod) that didn't have them. Fixed properly: `Create_mlrt_trt` now explicitly `LoadLibraryExA`s `nvinfer_10.dll` (with `LOAD_WITH_ALTERED_SEARCH_PATH`, so *its* dependencies also resolve from the same folder) from a path derived from `mlrt_trt.dll`'s own module location (`GetModuleHandleExA(GET_MODULE_HANDLE_EX_FLAG_FROM_ADDRESS, ...)`), before anything else touches TensorRT — mirrors `mlrt_ort.cpp`'s existing `LoadLibraryA`-by-own-path convention for `onnxruntime.dll` et al. The plugin is now self-sufficient: just keep `nvinfer_10.dll` + its CUDA/cuDNN runtime DLLs (from `vsmlrt_bench\plugins\vsmlrt-cuda\`) sitting next to `mlrt_trt.dll` — no more copying them into every host app's own folder.

### The performance bug that cost most of the debugging time: `Prefetch()` thread count vs. `num_streams`

Initial benchmark attempt (`Prefetch(16, 20)`, `num_streams=4` — copying the VapourSynth-side benchmark's `core.num_threads=16`/`num_streams=4` config verbatim) measured **catastrophically slow**: 5-13 **seconds** per inference call (vs. an expected ~40-50ms), i.e. 100-250x slower than sequential. Root-caused via temporary `std::chrono` timing instrumentation added around each pipeline stage in `get_frame_mlrt_trt` (gated behind `MLRT_TRT_TIMING=1` env var, cheap — one bool check per frame, cached at `Create_` time — left in the shipped code since it's useful):

- This machine has **6 physical cores / 12 logical threads** (`wmic cpu get NumberOfCores,NumberOfLogicalProcessors`) — `Prefetch(16, ...)` requests 16 AviSynth worker threads, oversubscribing by 4 threads.
- Setting `cudaSetDeviceFlags(cudaDeviceScheduleBlockingSync)` before the device context is created (the default `cudaStreamSynchronize` scheduling policy can busy-spin rather than block, which compounds badly under thread oversubscription) is now in the code as a real fix, but did **not** fully resolve the pathology alone.
- The actual fix was tuning **both** knobs down to what the hardware can support: `Prefetch(4, 8)` + `num_streams=2` → **healthy ~27 inference calls/sec**, matching the VapourSynth-side benchmark's throughput almost exactly (25.85 calls/sec equivalent).
- `num_streams=4` remained bad (**0.15x-0.17x**, i.e. still ~10x slower than `num_streams=2`) **even with a sane thread count** (`Prefetch(8,12)`) — this points to genuine GPU-side contention from 4 concurrent execution contexts on this specific 8GB card/engine, not just host thread oversubscription. Didn't dig further into why; `num_streams=2` is the validated sweet spot on this hardware.
- **Takeaway for whoever tunes this next**: don't copy `Prefetch`/`num_streams` numbers between VapourSynth and AviSynth benchmarks assuming they transfer — VapourSynth's internal thread-pool scheduling and AviSynth's `Prefetch()` (real OS threads, one per prefetch slot) behave differently enough under oversubscription that the "right" numbers aren't the same. Always check `wmic cpu get NumberOfCores,NumberOfLogicalProcessors` (or equivalent) first and start at or below that.

## Critical finding (2026-08-10): the cached `3ce179f1.engine` (RIFE v4.4) produces bad output on real footage — use v4.9 instead

All benchmarking above used synthetic `BlankClip` content (flat color + a moving text overlay) and looked fine. Running the actual pipeline on **real video** (`C:\Temp\Kürbiskernernte.MP4`) revealed a severe defect: **every interpolated frame has a dense, regular grid of thin dark lines over the entire image** (period ≈4px, consistent with a checkerboard artifact from a strided upsampling/`ConvTranspose` layer — the RIFE v1-implementation graph has 4 of these). Passthrough (non-interpolated) frames are unaffected — confirmed by inspecting extracted PNGs directly.

**Root cause isolated, not a bug in this port.** Reproduced identically via four independent paths, ruling out `mlrt_trt.cpp`, AviSynth, and precision:
1. `mlrt_trt.dll` (this project) — the original finding.
2. The **official** VapourSynth `vstrt.Model` plugin (`AmusementClub/vs-mlrt`'s own binary) loading the exact same `.engine` file directly.
3. The **official** `vsmlrt.RIFEMerge()` Python API, building a **fresh fp32** engine from `rife_v4.4.onnx` (ruling out fp16 precision as the cause — checked because of a superficially-similar, but different, known issue: [vs-mlrt#66](https://github.com/AmusementClub/vs-mlrt/issues/66), which is about int64→fp32 casts in the *implementation-2* graph; `rife_v4.4.onnx`'s implementation-1 graph has no `Cast`/`Reciprocal` ops at all — checked via `onnx.load()` — so that specific issue doesn't apply here).
4. Rebuilding with `--tacticSources=+CUBLAS,+CUBLAS_LT,+CUDNN,...` (forcing different kernel selection) — no change.

## Portable deployment package for ffastrans render nodes (2026-08-10)

Built a self-contained deployment folder: **`D:\dev\avs_rife_tensor\deploy\mlrt_trt\`** (~568MB, see its own `README.md` for full details). Goal was "100% portable" per user request — no VC++ redistributable install, no CUDA Toolkit/TensorRT SDK install, works regardless of which host application (ffastrans's own binary, ffmpeg, AvsPmod, ...) loads the plugin or from what directory.

**Two source-level portability bugs found and fixed** (both in `avs-mlrt/mlrt_trt/`, both are the same underlying class of problem the v4.4-era `nvinfer_10.dll` fix already solved for one DLL, generalized here to the rest):
1. **VC++ CRT dependency.** `dumpbin /dependents` on the previously-built `mlrt_trt.dll` showed direct imports on `MSVCP140.dll`, `MSVCP140_ATOMIC_WAIT.dll`, `VCRUNTIME140.dll`, `VCRUNTIME140_1.dll` — the VC++ redistributable, *not* part of Windows itself. This machine happens to already have it installed system-wide (confirmed via `C:\Windows\System32\msvcp140.dll` etc. existing), which would have silently masked the bug in naive testing — a fresh render node without it installed would fail to even load the plugin. **Fix:** `mlrt_trt/CMakeLists.txt` now sets `MSVC_RUNTIME_LIBRARY "MultiThreaded$<$<CONFIG:Debug>:Debug>"` (i.e. `/MT`, static CRT). Rebuilt DLL's only direct import is now `KERNEL32.dll`.
2. **`cudart64_13.dll` isn't a delay-load import, it's not a PE import at all.** Expected `cudart` (linked in `CMakeLists.txt`) to show up as either a direct or `/DELAYLOAD` import, matching `nvinfer_10.dll`'s handling — but `dumpbin /dependents` showed neither. Modern CUDA's `cudart.lib` apparently performs its own internal, path-less `LoadLibraryA("cudart64_13.dll")` on first runtime-API call (invisible to the PE import table, NVIDIA's own lazy-binding mechanism) — which hits the *exact same* "resolves relative to the host app's directory, not the plugin's" problem as the original `nvinfer_10.dll` bug, just one level less visible. **Fix:** generalized the existing `getOwnModuleDirectory()`-based preload into a `preloadFromOwnDirectory()` helper (`mlrt_trt.cpp`), called for `cudart64_13.dll` *and* `nvinfer_10.dll`, in that order, at the very top of `Create_mlrt_trt` before anything touches CUDA/TensorRT. Once explicitly loaded by absolute path, any later bare `LoadLibraryA("cudart64_13.dll")` call (ours or NVIDIA's internal one) just finds the already-loaded module by name — Windows doesn't re-search the filesystem for a module already loaded in the process, so this closes the gap regardless of who triggers the later call.

**Minimal runtime DLL set determined empirically** (not guessed): in an isolated folder containing *only* `mlrt_trt.dll` + candidates, with this machine's `PATH`/`System32` confirmed to have zero CUDA/TensorRT files that could mask a missing-dependency bug, real inference (all 4 bundled RIFE versions) succeeded with **exactly 3 files**: `mlrt_trt.dll`, `nvinfer_10.dll`, `cudart64_13.dll`. Also verified pixel-identical output vs. the full `vsmlrt-cuda` runtime folder, and verified host-independence by running the same script through two unrelated `ffmpeg` builds in unrelated directories. **Not needed at runtime** (confirmed by their absence not breaking anything): cuBLAS/cuBLAS_LT/cuDNN DLLs (consistent with the `-CUBLAS,-CUBLAS_LT,-CUDNN` tactic sources used when building these engines), `nvinfer_plugin_10.dll`, `nvonnxparser_10.dll`, `nvrtc*.dll`, and — the big size win — all `nvinfer_builder_resource_*.dll` files (one per GPU arch, ~150-450MB each; these are `trtexec`/engine-*build*-time only, since `mlrt_trt` only ever loads a pre-built `.engine`, confirming the CMakeLists/handoff-doc division of labor was correct). This shrinks a real deployment from vs-mlrt's full ~3.7GB `vsmlrt-cuda` bundle down to ~570MB, almost all of which is `nvinfer_10.dll` itself (376MB).

**Deliberately NOT addressed — flagged prominently in the deploy README instead of silently working around it:** TensorRT `.engine` files are tied to the exact GPU arch/driver/TensorRT version they were built on (this machine: RTX 5050 `sm_120`, driver 591.86, TensorRT 10.16.0). The bundled engines will not work as-is on a render farm with different GPUs — each distinct target needs its own `trtexec` build (command included in the README). Didn't attempt to solve this (e.g. via on-first-run engine building) since it's out of scope for "package what already works" and depends on facts about the target farm this session doesn't have.

## On-demand engine build+cache for arbitrary source resolutions (2026-08-10)

The deploy package above assumed a known, fixed resolution (1920x1088). Told that ffastrans source material "can be literally anything," which breaks that assumption outright: a static-shape TensorRT engine only runs at the exact frame size it was built for, and — checked directly in `vsmlrt.py`'s `RIFEMerge()` — RIFE explicitly does **not** support tiling as a workaround (`"tiling is not supported"`, since optical-flow estimation needs full-frame context and tiling would create seams). So the only real options were (a) one engine per resolution built ahead of time — impossible for "anything" — or (b) a dynamic-shape engine with committed-upfront bounds, untested here, or (c) build-and-cache on demand, mirroring what `vsmlrt.py` itself already does (`get_engine_path()`/`trtexec()`). User picked (c).

**Implemented directly in `mlrt_trt.cpp`** (not the `.avsi` wrapper — AviSynth+ script has no built-in way to shell out and block on a subprocess): `mlrt_trt`'s `engine_path` parameter is now genuinely optional. New behavior in `resolveOrBuildEngine()`:
- `engine_path` given and exists → load as-is (unchanged, zero behavior change for existing callers).
- `engine_path` given but missing, `onnx_path` also given → build to exactly that path.
- `engine_path` empty/omitted, `onnx_path` given → a path is derived next to the ONNX file, named `<onnx_stem>_<gpu_name>_trt<version>_<W>x<H>_fp16.engine` (GPU name via `cudaGetDeviceProperties`, TRT version via the global `getInferLibVersion()` — NOT `nvinfer1::getInferLibVersion()`, it's outside that namespace despite living in an nvinfer header) — loaded if it already exists, else built there.
- Neither given → error.

Building shells out to `trtexec.exe` via `CreateProcessA` (`runProcessSync()`, blocking — acceptable since this only runs once at script-parse time, not per frame), stdout+stderr redirected to a temp file for error-message capture on failure, using the exact same validated flags from the manual builds earlier this session (`--fp16 --tacticSources=-CUBLAS,-CUBLAS_LT,-CUDNN,+EDGE_MASK_CONVOLUTIONS,+JIT_CONVOLUTIONS --noTF32 --inputIOFormats=fp32:chw --outputIOFormats=fp32:chw --builderOptimizationLevel=3`), with `--shapes` sized to the clip's actual (post-padding) width/height. Builds go to a per-process-unique `<final_path>.<pid>.building` temp name first, then `MoveFileExA`'d into place — if a second process racing to build the identical (new resolution, first-seen) engine finishes first, the loser just deletes its own redundant copy and uses the winner's file, rather than corrupting anything. `trtexec.exe` itself only needs `KERNEL32.dll` directly (it's a standalone process, not a loaded plugin, so the host-app-relative-search-path problem that necessitated the `LoadLibraryExA` tricks elsewhere doesn't apply to it — its own directory works as the search root out of the box).

**Empirically found the minimal builder-time DLL set** the same way as the inference-time set earlier: `trtexec.exe` + `nvinfer_10.dll` + `cudart64_13.dll` + `nvonnxparser_10.dll` + `nvinfer_builder_resource_sm120_10.dll` (this GPU's arch — **not portable to other GPU archs**, would need the matching variant swapped in) + `nvinfer_plugin_10.dll` (trtexec unconditionally does "Loading standard plugins" and hard-fails without this one, even though nothing in the RIFE graph itself needs a plugin). No cuBLAS/cuDNN/nvrtc needed at build time either, consistent with the tactic sources excluding them. Verified the resulting on-demand-built engine's output is correct (near-zero diff vs. the manually-built reference, consistent with normal build-to-build tactic-selection nondeterminism) before wiring it into the plugin.

**`.avsi` wrapper (`mlrt_RIFE_trt.avsi`) updated non-breakingly:** added optional `onnx_path`/`trtexec_path` params threaded through to the underlying `mlrt_trt(...)` call. Deliberately did NOT reorder existing parameters (which would have broken the documented positional-call convention, `mlrt_RIFE_trt(c, engine_path, implementation, ...)`) — instead, existing callers pass a real `engine_path` and are completely unaffected; new arbitrary-resolution callers pass `engine_path=""` plus `onnx_path=...`.

**Deploy package (`deploy\mlrt_trt\`) grown from ~570MB to ~984MB** to carry the on-demand path: added `trtexec.exe`, the 3 extra builder-time DLLs, and the ONNX source files (previously only the pre-built `.engine`s shipped). README rewritten to lead with the on-demand mode as the recommended default for ffastrans (arbitrary resolutions), keep the pre-built engines as a latency optimization for the one known resolution tested, and flag prominently that `nvinfer_builder_resource_sm120_10.dll` — unlike the inference-only DLLs — is GPU-architecture-specific and won't work for on-demand building on a differently-archable render node (inference of an already-built/cached engine is unaffected).

**Tested end-to-end from the actual shipped deploy folder** (not just a scratch dir) at two brand-new resolutions never built before (1280x736 padded, 960x544 padded) — cold build ~90-100s, warm re-run ~3-4s (cache hit), output visually artifact-free both times.

This is a real effect, not a reporting artifact: a higher target fps means synthesizing proportionally more distinct output frames per second of source footage, so the GPU does proportionally more actual RIFE inference work — going from 25fps to 50fps output is 2x the frame rate and empirically ~2x the wall-clock cost per second of source video. The dual-socket-CPU tangent noted below this entry previously was a red herring; this is the real explanation. **Practical upshot: `speed=` numbers from this pipeline are only comparable at the same target output fps** — don't compare a 25fps-target benchmark against a 50fps-target one and call it a regression. If a future session needs a faster "realtime" number and the true deliverable allows a lower output fps, that's a legitimate, large lever (not just a benchmark trick) — confirmed empirically here, not merely theorized.

**Correctness check on `rife_v4.17_lite`** (the winner), following this project's own established bar (the v4.4 checkerboard-bug precedent means "looks fine on a quick look" isn't good enough): extracted 5 consecutive real-footage output frames (`ffmpeg -vf "select='between(n,300,304)'"`), full-frame visual check plus a cropped+contrast-boosted+sharpened zoom (to surface subtle periodic/checkerboard patterns the full-frame view could hide) — clean, no grid artifact, matches the full `rife_v4.17` output at the same frames by eye. Objective check: PSNR ~27.0dB / SSIM ~0.934 between `v4.17_lite` and full `v4.17` output on those frames — a real, moderate divergence (expected for a reduced-capacity "lite" architecture trading some fidelity for speed) but with no artifact-type spatial structure (a broken kernel like the v4.4 bug shows up as a very characteristic, very low-PSNR periodic pattern, not this kind of diffuse gap). **Caveat: only checked on one near-static (slow drone pan) segment of the test clip** — didn't specifically hunt for a high-motion segment, which is where lite-model quality trade-offs (and any residual artifact) would show up most. Worth a spot-check on faster motion before shipping.

**Not done:** the other lite variants (`v4.12` through `v4.16_lite`) weren't downloaded/tested — `v4.17_lite` already beat every full model tested including the previous speed leader (`v4.9`), so there was a clear answer without exhausting the whole lite family, but an earlier lite version could in principle be faster still (smaller architecture generation) at some further quality cost.

## Bigger real win: `implementation=2` (2026-08-11)

User pushed back that 0.48-0.58x realtime is "extremely slow" and asked for genuinely faster options, not just the ones already tried. Checked GPU clocks/power/thermal during load first, to rule out an artificial limiter before concluding the GPU ceiling was real: `nvidia-smi` logging during a run showed **SM clock at ~2947MHz (95% of the 3090MHz max), power draw only ~93W of the 130W limit, temperature topping out at 62°C, no throttle reasons active** — so the GPU genuinely isn't clock/power/thermal-limited; the ceiling found in earlier sessions was real compute demand, not a tunable limiter. That ruled out easy wins and meant the real lever had to be reducing the actual FLOPs per frame.

`implementation=2` (the 7-plane, internal-padding RIFE graph — `rife_v2/` in each model's archive, as opposed to `implementation=1`'s 11-plane positional-encoding graph in `rife/`) had been flagged since 2026-08-10 as "not tested end-to-end" and was the obvious untried candidate: it skips the horizontal/vertical/multiplier_h/multiplier_v positional-encoding input planes and their construction entirely. Built a `rife_v4.17_lite` engine from `rife_v2/rife_v4.17_lite.onnx` (same fp16/tactic flags as always, `--shapes=input:1x7x1088x1920` — 7 channels instead of 11). `trtexec`'s own isolated GPU compute time dropped from 26.7ms (`implementation=1`) to **17.3ms (`implementation=2`)** — a ~35% cut. End-to-end in the real pipeline (same benchmark methodology, 900 frames, `num_streams=2`, `Prefetch(4,8)`): **0.683x**, rising to **0.687-0.688x with `use_cuda_graph=true` layered on top** (that flag's small ~1% effect is additive, not specific to one implementation). That's ~17% faster than the same model via `implementation=1` (0.584x) and **~42% faster than where this whole investigation started today** (full `rife_v4.17` via `implementation=1`, 0.481x).

Verified visually clean using the same methodology as every other model check in this project (full-frame look + a cropped/contrast-boosted/sharpened zoom to surface subtle periodic artifacts): no checkerboard/grid pattern. PSNR ~28.6dB/SSIM~0.95 vs. the same model's `implementation=1` output on identical frames — a real, moderate difference (different network graph, different padding strategy) but not the artifact-shaped signature a broken kernel would leave. **Same caveat as the lite-model check: only tested on a low-motion clip segment so far.**

Added to the deploy package as `deploy\mlrt_trt\models\rife_v2\rife_v4.17_lite_fp16.engine` (both direct-`engine_path` and on-demand-cache naming forms), documented in the deploy README as the fastest verified-clean option found in this project to date.

**Not done / real remaining option:** `implementation=2` doesn't need mod32 padding at all (it pads internally) — this session's test still padded to 1088 (kept for apples-to-apples comparison against the `implementation=1` numbers), so testing at native 1920x1080 (skipping `AddBorders`/`Crop` entirely) is a small additional win nobody's measured yet. Also didn't try `implementation=2` combined with other model versions (full `v4.17`, `v4.9`'s `rife_v2` graph if one exists) — the ~35% raw-compute cut from dropping to 7 planes is presumably somewhat model-version-independent, so it's a reasonable bet it'd help elsewhere too, just not verified.

## Session (2026-08-12/13): chasing 1x realtime — what was tried, what worked, what's still open

Starting point this session: `rife_v4.17_lite`, `implementation=2`, fp32-IO engine, `Prefetch(4,8)`/`num_streams=2` — the config documented above at **0.683-0.688x**. Goal: get to minimum 1x realtime at the 50fps target. Ended the session at **0.871x confirmed, with a further untested idea that could close the rest of the gap** — see "Open, not yet validated" below before trusting anything past that point.

### Dead ends (real findings, not abandoned-without-checking)

All of these were empirically tested, not just reasoned about — several disproved my own initial hypothesis, which is exactly why they're worth recording rather than silently dropping.

1. **fp16 TensorRT engine I/O (input/output tensors, not just internal compute).** Hypothesis: the engine's I/O bindings were fp32 even though compute already runs fp16 (`--fp16` builder flag), so halving the H2D/D2H transfer size should help. Isolated `trtexec` test confirmed the transfer-time halving is real (H2D 8.5ms→4.3ms, D2H 3.5ms→1.75ms) but GPU Compute Time was unchanged (~17.3ms either way) — TensorRT was already casting internally regardless of the declared binding width. Wired it into the actual plugin anyway (added real fp32↔fp16 pack/unpack in `inference_helper.h`'s tile-copy loop, engine-side byte-width tracked separately from AviSynth's fixed fp32 `bytes_per_sample`) since AviSynth has no native fp16 clip type and the conversion has to happen somewhere. Real-pipeline result: **~22% *slower*** (0.533x vs 0.679x baseline), confirmed via `nvidia-smi dmon` — GPU utilization dropped from 99% to ~33-69% (avg ~47%), meaning the bottleneck moved from GPU to the CPU-side scalar fp32/fp16 conversion (a portable bit-manipulation implementation, no SIMD/F16C intrinsics — that's the likely fixable part if this is ever revisited, but wasn't attempted). Correctness was fine (PSNR 58dB vs. fp32 baseline, pure rounding noise) — the idea failed on performance, not correctness. **Fully reverted**: `inference_helper.h` and `mlrt_trt.cpp` restored to their pre-experiment content, DLL rebuilt from reverted source and redeployed to both `test/` and `deploy/mlrt_trt/`, all engine/test artifacts from this experiment deleted.
2. **Batched inference (batch>1 in a single TensorRT engine).** Blocked at the ONNX-export level, not a performance question. `implementation=1` (11-plane): every version from v4.0 through v4.22 declares its input shape with a **hardcoded literal batch=1** (`[1, 11, -1, -1]`) — TensorRT rejects any other batch size outright. `implementation=2` (7-plane, the one actually shipping): declares a symbolic `batch` dim, but tested across three different model versions/sizes (`v4.17_lite`, `v4.22`, `v4.22_lite`) — **all three fail at the identical node** (`/Reshape_11`, "reshape changes volume to multiple of original non-zero volume"). Traced the actual cause: the graph stacks the two source frames along channels (6ch = 3+3) then reshapes them into a *virtual batch of 2* (`[N,6,H,W]→[2,3,H,W]`) so a shared-weight encoder can process both frames via one batched conv call — a real, sensible architectural trick, but the `2` was baked in as a literal during PyTorch tracing (traced at batch=1, so `1×2=2` collapsed to a constant) instead of staying a dynamic `batch×2` expression. Scanning the whole graph found **17 instances of this same pattern across 12 distinct `Reshape` nodes** (RIFE's coarse-to-fine architecture repeats similar refinement blocks), with a mix of legitimately-fixed constants (channel counts) and actually-broken ones (batch-dependent) that can't be told apart without the original PyTorch source — get even one wrong and the failure mode is silent, per-pixel-plausible corruption, not a crash (exactly the class of bug the v4.4 checkerboard artifact was). Concluded this isn't worth guess-patching; would need either a proper PyTorch re-export with correct dynamic-batch tracing, or accepting the risk of hand-patching 12 sites blind. **Not attempted further, no files changed.**
3. **TensorRT-RTX** (`tensorrt_rtx.exe`/`tensorrt_rtx_1_4.dll`, already bundled in `vsmlrt-cuda`). Built+benchmarked the same model/shape: **69% slower** (29.28ms vs 17.32ms GPU compute time). Makes sense in hindsight — TensorRT-RTX trades peak performance for cross-shape/cross-GPU portability (JIT kernel specialization at load time) rather than the full ahead-of-time tactic search a static-shape `trtexec` build already gets; exactly the opposite trade a fixed shape/fixed GPU deployment wants. Ruled out.
4. **Exhaustive `trtexec` builder-flag sweep**, all via isolated builds (no plugin involvement), all compared against the 17.32ms baseline GPU Compute Time: builder optimization level 5 vs 3 (no change), all tactic sources enabled (slightly worse), cuDNN/cuBLAS re-enabled (worse), `maxAuxStreams=2` (worse), `tilingOptimizationLevel=3` (didn't finish building in 5 min), native 1920×1080 resolution instead of the mod32-padded 1088 (`implementation=2` doesn't need the padding but pads internally anyway — slightly *worse*, 1088 is better-aligned for tiling), `persistentCacheRatio=0.5` (no change), 2G workspace pool (no change). **Conclusion: the config already in production is genuinely at this GPU's ceiling for every TensorRT-level tuning knob.**
5. **INT8 quantization** (mixed fp16/int8, trtexec's own best-effort dynamic range, no real calibration dataset). **68% slower** (28.97ms vs 17.32ms) — a small network like this pays real quantize/dequantize reformatting overhead between fp16 and int8 layers that swamps whatever arithmetic savings int8 offers. The gap is far too large for a proper calibration pipeline to plausibly close, so not worth the real accuracy risk a calibration effort would carry for a RIFE optical-flow model. Ruled out without building a calibration pipeline.

### The real win: relabeling 29.97→30fps before the RIFE retiming math (`AssumeFPS`)

The general (non-integer-ratio) fps-conversion branch in `mlrt_RIFE_trt.avsi` (~line 153 on) already skips the RIFE call entirely on any output frame whose interpolation timepoint lands exactly on a source frame (confirmed via the plugin's `MLRT_TRT_TIMING=1` instrumentation — frame 0 is completely absent from the per-frame timing log when `frac==0`). The catch: how *often* that happens is purely a function of how cleanly `src_fps/dst_fps` reduces. True 29.97fps (30000/1001) against 50fps reduces to `600/1001` — coprime, huge denominator — so the exact-match rate is only **1-in-1001 (~0.1%)**.

Relabeling the source as exactly 30fps via `AssumeFPS(c, 30, 1)` (a pure metadata change, no pixel data touched, applied once right after decode) changes that ratio to `30/50 = 3/5` — denominator 5, giving a **1-in-5 (20%) exact-match rate**. Proved by brute-force search (`fractions.Fraction` over all `F = 50a/b` for `b` up to 40 within a generous ±15% band of 29.97) that **no other "near" framerate beats this** — the only candidate with a better hit rate is 33.33fps (33%), which is an 11.2% speed distortion (obviously perceptible, not a rounding trick), two orders of magnitude past 30fps's 0.1% distortion. 30 is the unique point where "close to the true source rate" and "shares a large common factor with the 50fps target" (both are multiples of 10) coincide.

**Empirically validated, not just derived:** ran with `MLRT_TRT_TIMING=1` and confirmed the exact predicted skip pattern (frames 0, 5, 10, 15, 20, ... missing from the log — precisely every 5th frame). Quality cost: zero for the skipped frames themselves (they're the literal, unmodified source frame, not an approximation of one) — the only cost is a global ~0.1% timing/duration stretch of the whole clip (~34ms drift over this 34s test clip), which matters only if audio gets muxed back in against the original 29.97 timeline downstream; a pure video pass has no issue with it.

**Surprise finding: the naive "skip 20% of GPU calls → ~25% faster" math didn't hold at the old `Prefetch(4,8)` tuning** — measured only +4.8% (0.673x→0.705x). Isolated the cause empirically: built a 100%-skip (zero-RIFE) version of the same colorspace/retiming pipeline and measured it at 2.29x realtime (~8.7ms/frame pure CPU cost) — not free, but far cheaper than the ~29.7ms/frame a real RIFE call costs. A weighted-average model using those real numbers (`0.8×29.7 + 0.2×8.7 ≈ 25.5ms/frame`) predicts ~0.78x, still short of what was measured — pointing at a **second real effect**: `Prefetch(4,8)` was tuned for a *uniform*-cost workload (every frame ~30ms), and mixing heavy (30ms GPU) and light (9ms CPU-only) frame costs into the same fixed buffer depth doesn't achieve ideal overlap. **Retuning `Prefetch` for the new, non-uniform cost profile recovered the rest of the gap**: swept `Prefetch(6,10)` through `Prefetch(12,24)` — `Prefetch(8,16)` is the best found, **0.871x**, a real **+29.4%** over the session's starting baseline. Confirmed the previously-documented oversubscription cliff still exists at this thread count too: `Prefetch(12,24)` collapsed to 0.096x, same pathology as before.

**Final validated config this session:** `rife_v4.17_lite`, `implementation=2`, fp32-IO engine (unchanged), `AssumeFPS(c, 30, 1)` right after decode, `Prefetch(8,16)`, `num_streams=2` (unchanged) → **0.871x realtime**, up from 0.683-0.688x at session start. Test script: `test/test_assumefps30_tuned.avs` (uses `Prefetch(6,12)` — the *0.871x number used `Prefetch(8,16)`, not yet copied into a saved script — see open items below).

### Duration-drift fix for `AssumeFPS(30,1)`, validated end-to-end (2026-08-13)

`AssumeFPS(30,1)` (used above for the RIFE-skip speed win) compresses the retiming clock by a factor of 1000/1001 relative to the source's true 29.97fps, so a naively 50/1-labeled output is ~0.1% (~34ms on this 34s clip) short of the source's true duration -- flagged as a known caveat since the technique was adopted, not previously fixed.

**User requirement: the deliverable needs literal 50.000fps CFR, not just correct duration** -- ruling out the simplest fix (relabeling the AviSynth output at `50000/1001`, the exact rate that cancels the compression losslessly, but which is nominally ~49.950fps, not 50).

**Fix: two-stage rate handling, the same technique broadcast pipelines use for 23.976<->24 / 29.97<->30 conversions.** In the `.avs` script, label the RIFE output honestly at its duration-correct rate (`AssumeFPS(c, 50000, 1001)` right after the `mlrt_RIFE_trt` call -- pure metadata, no resample, no cost) instead of forcing a lying 50/1. Then, at the actual encode step, let ffmpeg's `fps` filter (`-vf fps=50`) do the real CFR conversion to true 50.000fps -- it inserts/drops frames at the mathematically correct sparse positions to hit the target rate while preserving the input's timeline, which (because the input is now duration-correct) means it also preserves the correct total duration. The math: since the 30:50 retiming is an exact 3:5 ratio, this reduces to exactly **one duplicated frame per 1000 output frames** (~once every 20s) -- a negligible, imperceptible correction, well inside the class of thing NTSC drop-frame timecode already does routinely.

**Validated on the full 1021-frame clip** (`test/test_real_video.avs`, now includes the `AssumeFPS(c, 50000, 1001)` relabel; encoded via `ffmpeg -i test_real_video.avs -vf fps=50 -c:v libx264 ...`): output measured via `ffprobe` at exactly **`r_frame_rate=50/1`** (satisfies the CFR requirement), **1703 frames, 34.060s total duration** vs. the source's true **34.067367s** -- residual gap **~7.4ms**, down from the original ~34ms (about 4.6x tighter). The remaining ~7ms is the unavoidable quantization of correcting in whole 20ms (1/50s) frame steps on a fixed-CFR grid -- as good as achievable without abandoning strict CFR, and well under any perceptible A/V sync threshold.

**Not yet done:** this two-stage relabel isn't baked into `deploy/mlrt_trt/scripts/mlrt_RIFE_trt.avsi` or documented as part of the "adopted default" recipe in the deploy README beyond a pointer to this section -- whoever wires the full recommended config (`AssumeFPS(30,1)` + `use_cuda_graph=true` + `Prefetch(8,16)`/`num_streams=2` + this duration fix) into the real ffastrans pipeline needs to include both the AviSynth-side relabel and the `-vf fps=50` ffmpeg encode flag together; using either alone doesn't get both the correct rate and the correct duration.
